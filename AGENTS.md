Static PWA (no build step): `index.html`, `styles.css`, `app.js`, `manifest.json`, `icon.svg`, `sw.js`. All logic is one vanilla-JS file (`app.js`, ~2,612 lines, no modules). There is no `package.json`, npm, linter, or test suite — do not invent build/lint/test commands.

## Deploy

## Release procedure — CRITICAL

Every release must bump **both**:
1. `const APP_VERSION = 'vN'` in `app.js` (shown in Settings; also cached into the SW URL via `./sw.js?ev=...`).
2. `const CACHE = 'ev-cache-vN'` in `sw.js` (must match).

`sw.js` uses stale-while-revalidate: cached assets are served instantly and `app.js`/`styles.css` are only refreshed when the cache name changes (activate deletes all other caches). Forgetting the `sw.js` bump means users keep running the old code indefinitely.

## Service-worker reload quirk

`init()` auto-reloads once when a new SW installs, stashing the draft input in `sessionStorage` keys `ev.sw-reload` / `ev.sw-text`. Keep those keys and that flow intact, or you'll wipe users' in-progress messages on every update.

- Conversation compaction (v27+): `maybeSummarizeHistory(providerSucceeded)` runs fire-and-forget after each **successful** reply. When history is large (>~3000 estimated tokens in the older-than-`SUMMARY_KEEP` (8) portion and ≥`SUMMARY_MIN_GAP` (8) exchanges since last compaction), it folds the older **non-sensitive, non-failed** turns into `STORAGE.conversationSummary` (`ev.conversationSummary`) and slices `history` to the newest 8. The summary is injected into `buildSystem()` on every later request (all three providers), so old context survives while every provider's request stays small. v28 hardening: `summarizeOnce` falls back across providers (primary = the provider that just succeeded; on failure the other provider — keys checked, fresh accumulator per attempt; content is Gemini-safe so both directions are privacy-legal) and the compaction call uses `sendToGemini`'s `noRecover` flag (skip the ~21s 429 backoff; the flag itself was removed in v85 when the `recover()` burst was deleted). Large old portions are folded in **chunks** ≤`SUMMARY_CHUNK_EST` (2400 accurate tokens) as a rolling summary (each pass = `Previous summary + next chunk`, output truncated to `SUMMARY_MAX_CHARS`), so every turn is preserved while each call fits the fallback model's limit (Groq 8K TPM). Guards: `summarizing` reentry flag; slice only if `history.length` is unchanged (a new message during the flight skips the slice); failures are silent. v35: `summarizeOnce` gained an `openrouter` branch (key-checked, `SUMMARY_MAX_TOKENS` 800 via `sendToOpenRouter`) and falls back across all three providers (primary = the provider that just succeeded; on failure the other providers in key order); `maybeSummarizeHistory` picks OpenRouter when it was the provider that succeeded. v34: the trigger also fires on **exchange count** (`history.length - lastSummaryLen >= SUMMARY_MIN_GAP * 2`, i.e. at the 24-entry `trimHistory` cap) so short hands-free turns that never exceed `SUMMARY_TRIM_EST` still get folded into a summary; and if `summarizeOnce` fails with `e.rateLimited` (both providers hot — the classic post-fallback case), `maybeSummarizeHistory` **still slices history to the newest 8** (dropping the old portion with no new summary) so history stays bounded during rate-limit outages. `startNewConversation` clears the summary. If the whole overall deadline passes it still throws the hard `timeoutError` (`.timeout`), but if the first-token window elapses with no token while the overall budget is still open it throws a **soft** `softTimeoutError()` (`.timeout = true, .soft = true`). `sendToGroq`/`sendToOpenRouter`/`sendToGemini` model loops `continue` to the **next model** on `.soft` (Gemini skips its 3× recover burst for soft timeouts), and their all-models-failed tails rethrow `softTimeoutError()` (instead of a cryptic "All X models unavailable") so `performReply`'s `.timeout` routing decides. Net: a loaded `openai/gpt-oss-120b` (or a silent `nemotron`) falls through to the next model / OpenRouter within the shared 20s cap instead of failing with zero output. `timeoutThis()` also gained route context in its failure message (provider + `reason` phrase, e.g. "…budget (Groq — Gemini was already marked unavailable…)") and uses `REPLY_DEADLINE_MS`/`FIRST_TOKEN_MS` dynamically instead of a hardcoded "15s".
- Gemini MALFORMED_FUNCTION_CALL handling (v91): free flash models sometimes return `finishReason: MALFORMED_FUNCTION_CALL` (a broken `google_search` tool call) with an empty reply. `sendToGemini`'s recovery loop now retries that **same model WITHOUT the tool** (`useTools = malformed ? false : liveInfo`) to get a plain-text answer instead of repeating the broken tool call (the "keep tools in recovery" intent at the `!isModelUnavailable` block is overridden only for the MALFORMED case), and if it still fails it `continue`s to the **next Gemini model** instead of throwing the route away — so a malformed tool call no longer cascades into the Groq→OpenRouter fallback (which can't web-search and burns the 20s budget). Also added `shortErrReason(err)` (a compact terminal reason: timeout → "timed out after 20s", rate-limited, too-large, else `err.message`) and used it in the fallback message chain so a failed cascade no longer re-embeds the full upstream Gemini error text multiple times (e.g. no more doubled "Gemini returned an empty reply… — OpenRouter also failed: …").
- Slow/silent Gemini no longer dead-ends a turn (v92): the v88 `if (err.timeout) { timeoutThis(); return; }` shortcut in `performReply`'s Gemini catch sat *before* the `needsLiveInfo` guard and the `fallbackToGroq` path, so *any* Gemini timeout (hard **or** the v89/v90 "soft" first-token timeout, both `.timeout=true`) failed non-live turns immediately — a light turn's 2 Gemini models each burning `FIRST_TOKEN_MS` (2×10s ≈ the whole 20s budget) with zero tokens reproduced the same "couldn't finish within 20s (Gemini)" failure on every Retry, and a live turn got mislabeled the same way. The blanket shortcut is **removed**: (1) live-info turns that timeout now `failThis("Gemini timed out getting live data…")` honestly (Groq/OpenRouter still can't web-search, so no fallback); (2) non-live turns with zero streamed output (`err.timeout && !reply.trim()`) now hand off to `fallbackToGroq` — the 20s budget stays shared via `deadline`, so if Gemini ate it all, Groq's send throws `timeoutError` → `timeoutThis()` still caps total wait, but if budget remains Groq/OpenRouter answers in ~2s instead of failing. Deprioritization (new `GEMINI_SLOW_OUTAGE_MS` = 60s): a **hard** (`.soft` false) full-budget zero-output Gemini timeout calls `markProviderOut('gemini', GEMINI_SLOW_OUTAGE_MS)` so the *next* message routes around a chronically-slow/down Gemini instead of burning another 20s (`chooseProvider` → reason `gemini-out`); a soft (per-model, fell-through-and-succeeded) timeout and partial replies don't trigger it, and any later Gemini success clears it via the existing `clearProviderOut('gemini')`. Localized to app.js; both OpenRouter/Groq direct-branch `timeoutThis` shortcuts (single-provider, no fallback) are unchanged.
- Stuck-at-"thinking" regression fix (v93): v92's timeout fallback branch in `performReply`'s Gemini catch ended with `return` immediately after a **successful** `fallbackToGroq`, skipping the shared success tail (app.js: `busy = false; setStreamingUI(false); setStatus('online',''); flushDisplay; writeEvEntry; extractFacts; freshConversation = false`), so after a slow-Gemini soft-timeout the Groq fallback answered correctly but the UI stayed stuck on "thinking" forever and the reply was never persisted. The two fallback branches are merged into one: `geminiTimedOut`/`hardGeminiTimeout` (the `!err.soft` deprioritize flag) is computed up front, the single `fallbackToGroq(err)` on success falls through to the shared tail (no early `return`), and `markProviderOut('gemini', GEMINI_SLOW_OUTAGE_MS)` fires only for the hard-timeout case (success *or* failure). This is the same class of bug the v77-v78 cleanup-pass fixed; keep any new early-return success path in `performReply` landing on the shared tail.
- Google Lens (v93): one-tap camera capture → vision identification. A camera button `#btn-lens` ()) sits next to `#btn-attach` in the chat input row and a hidden `#lens-input` (`accept="image/*" capture="environment"`) opens the phone camera (Android/PWA). `handleLensCapture(file)` validates the image (`IMG_MIME_RE`/`attachmentError`), clears existing attachments, compresses via the shared `readFileAsDataURL`→`loadImage`→`imageToJPEG(img, 1024, 0.7)` pipeline, sets `lensPending = true`, and sends the fixed `LENS_PROMPT` ("Identify what is in this photo…"). In `send()`, a `lensPending` block pins the turn to a **vision-capable** provider (never OpenRouter — privacy invariant): Gemini when `settings.geminiKey && !isProviderOut('gemini')` and privacy isn't forced to Groq, else Groq (`reason = 'lens'`), else a "needs a Gemini (or Groq) key" failure with attachments cleared. `btn-lens` is ignored while `busy`; `lens-input` change resets the value before reusing.

## Privacy invariant (do not violate)

Sensitive content must **never** reach Gemini or OpenRouter. `analyzeSensitivity` → `chooseProvider` routes sensitive/private to Groq (OpenRouter free models may train on prompts, so it only ever sees **text-only, non-sensitive** turns; with no Groq key, sensitive content goes to Gemini as before). `buildMessages` skips `h.sensitive` history entries on the Gemini/OpenRouter routes; `visibleFacts` hides sensitive facts from non-Groq providers. Calendar results and anything keyword/PII-flagged ride this same rule. The conversation summary is built **only from non-sensitive, non-failed turns**, so it is Gemini/OpenRouter-safe by construction — sensitive turns keep raw context only while inside the recent window (they age out once folded/trimmed). Keep new features consistent.

## Free-tier token budgets & rate-limit handling

Estimate is `Math.ceil(text.length / 4)`, which undercounts real Groq tokens by ~1.7× (e.g. estimated 7,264 → Groq counted 12,349). Budget constants (`GROQ_TEXT_BUDGET`, `GROQ_TIGHT_TEXT_BUDGET`, `GROQ_IMAGE_BUDGET`) and `fitOpenAITextBudget`/`openAISendFitted` handle trimming + retry-on-TPM-too-large (`isTooLargeError`) for **both** Groq and OpenRouter. Don't casually raise these; they exist because the Groq free tier is 8K TPM. v35: the old `accurate` boolean became ratio constants — `ACCURATE_RATIO = 1.7` (summary/compaction path) and `TIGHT_RATIO = 2.0` (only `openAISendFitted`'s **tight-budget retry**: `fitOpenAITextBudget(provider, ..., GROQ_TIGHT_TEXT_BUDGET, TIGHT_RATIO)` — budget lowered 3600 → 3200), so the retry sends a request that genuinely fits the 8K TPM window. The primary send and the image path keep the optimistic (max-context) estimate. v28: the system prompt is bounded too — `visibleFacts` caps facts at `FACTS_EST_BUDGET` (800 est tokens, newest-first; sensitive filtered before the cap for Gemini), and stored facts are trimmed to newest 60 (at load + on `extractFacts`), because an unbounded facts section alone can blow past the 8K TPM window even in a fresh conversation (measured: 9,045-token rejection). TPM/too-large errors are reported as "too large" (not "rate-limited") with an actionable hint, on the fallback, direct-Groq, and OpenRouter paths. v34/v35 rate-limit handling: `rateLimitedError(detail, delay)` classifies a 429 as `err.tooLarge` / `err.rateLimited` / `err.dailyQuota` (`isDailyQuotaError`). 429s carry `err.retryDelayMs` (Groq `error.retryDelay` seconds parsed in `groqAttempt`, Gemini via `retrySecondsFrom`, OpenRouter via `Retry-After`); `rateLimitDelayMs()` floors unknown delays at `RATE_RETRY_DEFAULT_MS` (12s) and caps at `RATE_RETRY_MAX_MS` (90s). In `performReply`, a pure rate-limit failure (`bothRateLimited` from a Gemini→Groq/OpenRouter fallback, or a direct-Groq/OpenRouter 429) auto-retries up to `MAX_AUTO_RETRY` (2) times via `autoRetryRateLimit` — it writes a temporary failed entry, shows "Retrying automatically in Ns…" (real delay + raw `err.detail` when present) in the bubble/status/overlay, sleeps while keeping `busy` true (mic stays paused in hands-free, new sends blocked), then re-enters `performReply` with `retriesLeft - 1`; giving up falls through to `failThis` + the Retry button (with `rateHint(detail)` — daily-cap vs per-minute), and a fresh user-triggered Retry gets a new budget. Note `isTooLargeError` also matches TPM-429 text, so the rate-limited branch is checked **before** the too-large branch in the fallbacks. Daily-quota errors (`isDailyQuotaError`) skip the ~18s Gemini `recover()` loop and **rotate to the next of the 5 Gemini models** (~100 req/day); `providerOut`/`OUTAGE_MS` (300s) remember a dead provider (`markProviderOut` on total 429 failure) so `chooseProvider` routes around it, and every successful reply clears that memory (`clearProviderOut`).
