Static PWA (no build step): `index.html`, `styles.css`, `app.js`, `manifest.json`, `icon.svg`, `sw.js`. All logic is one vanilla-JS file (`app.js`, ~1,862 lines, no modules). There is no `package.json`, npm, linter, or test suite — do not invent build/lint/test commands.

## Release procedure — CRITICAL

Every release must bump **both**:
1. `const APP_VERSION = 'vN'` in `app.js` (shown in Settings; also cached into the SW URL via `./sw.js?ev=...`).
2. `const CACHE = 'ev-cache-vN'` in `sw.js` (must match).

`sw.js` uses stale-while-revalidate: cached assets are served instantly and `app.js`/`styles.css` are only refreshed when the cache name changes (activate deletes all other caches). Forgetting the `sw.js` bump means users keep running the old code indefinitely.

## Service-worker reload quirk

`init()` auto-reloads once when a new SW installs, stashing the draft input in `sessionStorage` keys `ev.sw-reload` / `ev.sw-text`. Keep those keys and that flow intact, or you'll wipe users' in-progress messages on every update.

## Architecture (app.js)

- Constants at top: model lists, sensitivity keywords, phone-command regexes, `STORAGE`/`DEFAULT_SETTINGS`, `APP_VERSION`, Groq budgets.
- `init()` at bottom is the entrypoint; `el.*` is the DOM element map.
- History entries: `{ role: 'user'|'ev', text, sensitive, ... }`. Failed replies persist as `{ failed: true, errorMsg, retryUserText, retryProvider, retryReason }` and are restored by `renderHistory()` with a working Retry button. Don't break the `entryRef`/`writeEvEntry` update path.
- Calendar lookup: phrase → `CALENDAR_RE` → webhook command `calendar` (MacroDroid Webhook trigger); MacroDroid reopens E.V as `https://elben08.github.io/E.V/?next={lvjson=evEvents}` (JSON list — query string so MacroDroid's "URL encode parameters" encodes it); `parseCalendarFragment()`/`init()` detect the JSON payload and render all events as `Title · <date>` lines (`formatEventDate`), still support the single-event `?next=&date=` form and legacy `#next=` hash, store the result as `{ role:'user', text:'[Calendar lookup result] …', sensitive: true }`, then clear the query/hash via `history.replaceState`. The result tab opens **in the background** (MacroDroid "Display over other apps"), so: `renderCalendarResult()` dedupes the history entry, and `speakWhenReady()` defers TTS until the tab is visible (background-tab `speechSynthesis.speak()` is silently dropped on Android). `calendarChannel` (`BroadcastChannel 'ev-calendar'`) forwards the result to any **visible** sibling tab, which renders + speaks it in the chat the user is actually looking at (keeps `sensitive:true` rule intact). All-day events (`"All day event": true` in the JSON) render **date only** via `formatEventDate(raw, allDay)`. MacroDroid config (5.65+ specifics) is in README and MACRODROID.md.
- Calendar constraints (verified on the live device/host, Aug 2026): MacroDroid 5.65 "Get Calendar Events" reads exactly **one** calendar per call — the picker has no "Any calendar"/multi-select. Device calendars: PC Sync (user's own events; selection stays here), a Gmail main calendar (same events via sync), and "Holidays in the Philippines" (separate calendar — NOT included unless selected; decision: holidays get added to PC Sync as recurring yearly events so a single read covers everything). Debug path: set Open Website URL to `?next={lv=evEvents}` (non-JSON) to dump the raw array as chat text. GitHub Pages hard-rejects URLs past **~8KB** with **414** (measured: 2/10/20 events OK, 30+ fail) and E.V never loads on 414 — each full-field MacroDroid JSON event is ~400 encoded chars, so ~20 events/lookup is the ceiling; if headroom is ever needed, compact the payload in MacroDroid to `Title`/`Start`/`All day event` only (~5× smaller).
- Phone control uses `triggerMacro(action)` → `fetch(<webhook> + '?cmd=' + action, { mode:'no-cors' })` where `<webhook>` is `settings.macroWebhook` normalized to end in `/ev_cmd` (accepts base or full URL). This is a MacroDroid **Webhook (URL)** trigger, since `intent://` can't reach MacroDroid's broadcast-receiver trigger. Actions are bare words: `calendar`, `flashlight.on`, `flashlight.off`, `wifi.on/off`, `bluetooth.on/off`. Returns an error string (shown as the reply) when no webhook URL is set. App launches still use `scheme=...;package=...;S.browser_fallback_url=...`.
- Hands-free voice (v29): optional `settings.handsFree` (default off; toggle in Settings → "Hands-free mode"). `toggleListening` → tap = session on/off when enabled; otherwise PTT as before. `startRecognition(mode)` ('ptt' | 'hands-free') uses `continuous:false` and auto-restarts (~400ms after end, 800ms after transient errors) to work around browsers stopping after ~1 min — the mic streams **only** while the session is active. Commands must start with a wake phrase (`WAKE_RE`: "hey E.V", "hey there E.V", "okay E.V", "E.V", etc.). v31: final segments accumulate across restarts into `handsFreeBuffer` (live in `vo-transcript`); `scheduleHandsFreeSend()` debounces the send to ~`HANDS_FREE_DELAY` (3000ms) after `handsFreeLastSpeech`, and the timer callback strips the wake phrase from the **combined** text (`stripWakePhrase` → `handleHandsFreeResult`), so a wake phrase split into its own segment (e.g. "Hey E.V" [pause] "what's the weather") still sends. `sawFinal` per session adds an interim-text fallback (`el['text-input'].value`, deduped) when no final result arrives. Ignored cases (bare wake word, no wake phrase) drop silently and keep listening; `EXIT_RE` (immediate per-segment and at timer fire) → `endHandsFreeSession()` (speaks "Hands-free off."). While busy or while E.V speaks, `busy`/`voice` blocks restart so the mic never hears its own reply; `resumeHandsFree()` restarts after the reply finishes (called from `speak()` done handler / `performReply` end / `failInBubble`). Exit anytime: tap the reactor, or say a `EXIT_RE` phrase ("stop listening", "exit hands-free", "goodbye", …). `saveSettingsForm` ends the session if Hands-free is saved off. `/not-allowed` mic denial ends the session. State vars: `handsFreeActive`, `handsFreePaused`, `handsfreeRestartTimer`, `handsfreeSendTimer`, `handsFreeBuffer`, `handsFreeLastSpeech` (never a hot loop — always gated by `handsFreeActive && !handsFreePaused && !busy`).
- Listening overlay (v30): fullscreen Siri/Jarvis-style `#voice-overlay` (midnight-navy radial bg, black `.vo-header` strip, `.vo-orb` with two cyan rings + `.vo-wave` of 13 cyan/pink bars via `voWave` keyframes, `.vo-transcript`, thin white `.vo-status`, `.vo-mic`). Shown for **both** PTT and hands-free whenever the mic is live (`onstart` → `setVoiceOverlay(true)`), live interim text goes to the input field **and** `vo-transcript` (`updateVoiceTranscript`); PTT hides it on `onend`/`onerror`; hands-free avoids flicker by staying up with the `.working` state (`setVoiceOverlay(true, true)`, pink ring, "Working…" label) set in `handleHandsFreeResult` and in `onend` while `handsFreePaused`, reverting to "Listening…" on `onstart` resume. v32: while a hands-free session is active (`handsFreeActive`), the overlay transcript also **streams the reply live** (from `performReply`'s `token` callback) and shows error text on failure (`failThis`), so the user can read the reply behind the overlay. Tap anywhere on the overlay = `toggleListening()` (stop PTT / exit hands-free), since it covers the reactor. `endHandsFreeSession()` and `/not-allowed` hide it. Z-index: 45 (above topbar/inputbar, below modals 50 / toast 60).
- Conversation compaction (v27+): `maybeSummarizeHistory(providerSucceeded)` runs fire-and-forget after each **successful** reply. When history is large (>~3000 estimated tokens in the older-than-`SUMMARY_KEEP` (8) portion and ≥`SUMMARY_MIN_GAP` (8) exchanges since last compaction), it folds the older **non-sensitive, non-failed** turns into `STORAGE.conversationSummary` (`ev.conversationSummary`) and slices `history` to the newest 8. The summary is injected into `buildSystem()` on every later request (both providers), so old context survives while both Gemini and Groq requests stay small. v28 hardening: `summarizeOnce` falls back across providers (primary = the provider that just succeeded; on failure the other provider — keys checked, fresh accumulator per attempt; content is Gemini-safe so both directions are privacy-legal) and the compaction call uses `sendToGemini`'s `noRecover` flag (skip the ~21s 429 backoff). Large old portions are folded in **chunks** ≤`SUMMARY_CHUNK_EST` (2400 accurate tokens) as a rolling summary (each pass = `Previous summary + next chunk`, output truncated to `SUMMARY_MAX_CHARS`), so every turn is preserved while each call fits the fallback model's limit (Groq 8K TPM). Guards: `summarizing` reentry flag; slice only if `history.length` is unchanged (a new message during the flight skips the slice); failures are silent. `startNewConversation` clears the summary. Note: `renderHistory` (reload) only re-renders the shrunken history, so older bubbles disappear from view after a reload — the summary is invisible but active.

## Privacy invariant (do not violate)

Sensitive content must **never** reach Gemini. `analyzeSensitivity` → `chooseProvider` routes sensitive/private to Groq. `buildMessages` skips `h.sensitive` history entries on the Gemini route; `visibleFacts` hides sensitive facts from Gemini. Calendar results and anything keyword/PII-flagged ride this same rule. The conversation summary is built **only from non-sensitive, non-failed turns**, so it is Gemini-safe by construction — sensitive turns keep raw context only while inside the recent window (they age out once folded/trimmed). Keep new features consistent.

## Groq free-tier token budgets

Estimate is `Math.ceil(text.length / 4)`, which undercounts real Groq tokens by ~1.7× (e.g. estimated 7,264 → Groq counted 12,349). Budget constants (`GROQ_TEXT_BUDGET`, `GROQ_TIGHT_TEXT_BUDGET`, `GROQ_IMAGE_BUDGET`) and `fitGroqTextBudget`/`groqSendFitted` handle trimming + retry-on-TPM-too-large (`isTooLargeError`). Don't casually raise these; they exist because Groq free tier is 8K TPM. Since v27, `estimateTokens`/`estimateMessagesTokens`/`fitGroqTextBudget` take an `accurate` flag that applies the ~1.7× real-token ratio; only `groqSendFitted`'s **tight-budget retry** uses it (`fitGroqTextBudget(..., GROQ_TIGHT_TEXT_BUDGET, true)`), so the retry sends a request that genuinely fits the 8K TPM window. The primary send and the image path keep the optimistic (max-context) estimate. v28: the system prompt is bounded too — `visibleFacts` caps facts at `FACTS_EST_BUDGET` (800 est tokens, newest-first; sensitive filtered before the cap for Gemini), and stored facts are trimmed to newest 60 (at load + on `extractFacts`), because an unbounded facts section alone can blow past the 8K TPM window even in a fresh conversation (measured: 9,045-token rejection). TPM/too-large errors are reported as "too large" (not "rate-limited") with an actionable hint, on both the fallback and direct-Groq paths.
